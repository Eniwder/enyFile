# Windows font fallback

採用構成（2026-11-08）: Slint 1.18.1 + Parley / Fontique 0.11.1の
PR #689相当バックポート、文字別キャッシュ上限8,192件。

選択フォントと標準候補に字形がないとき、表示対象の実文字をWindowsの
DirectWrite `MapCharacters()`へ渡す。補完先のフォント名・ファイル名はアプリで
固定しない。以前のMicrosoft YaHei / SimSunを`SLINT_FONT_PATH`へ指定する処理は
削除した。ユーザーが外部で設定したSlint環境変数までアプリで消去することはしない。

上流PRは確認時点では未マージだったため、依存2パッケージだけを
`app/Cargo.toml`の`[patch.crates-io]`で差し替える。由来、調整点、ライセンスと
移行手順は[app/vendor/README.md](../app/vendor/README.md)に記録している。
アプリ独自のフォント選択・描画や、フォントファイルの同梱はない。

## 最終構成の確認

- 簡体字`难・汉`、繁体字`繁體中文・龍門`、ハングル`한국어`、拡張漢字`𠀀`、
  記号`⟰・⨌`、絵文字`😀`を、Meiryo UI / Noto Sans JPの画面で確認。
- 日本語・英数字のUIスナップショットは未修正構成とピクセル単位で一致。
  5,000件のグリフID合計・字幅合計も一致。
- 本体テストに、OSが提供できる文字を通常のフォント選択・レイアウト経路で
  欠落させない回帰テストを追加。特定の中国語フォントのインストールを前提にしない。
- 81件の本体テストが成功。通常ビルドに研究用カウンターや診断用スイッチは含めない。
- フォント切り替え、設定プレビュー、実ファイルの一覧表示・ページ送り・キー移動も確認。

## 通常文字の約8%増について

旧測定の計数用Atomicを外し、未修正構成と最終構成を交互に**20組**実行した。
各プロセス内で5,000件の文字レイアウトを3周し、UIでは2ペイン・各24行のページを
巡回した。下表はプロセス単位の中央値。

| 日本語・英数字の条件 | 未修正 | 最終構成 | 比率 |
| --- | ---: | ---: | ---: |
| 5,000件の文字レイアウト（3周目） | 80.69ms | 83.15ms | +3.0% |
| 初回の名前ページ描画 | 15.85ms | 16.13ms | +1.7% |
| 5,000件の初回ページ巡回 | 1,959.55ms | 1,985.02ms | +1.3% |
| 5,000件の温まったページ巡回 | 1,945.67ms | 1,948.84ms | +0.16% |
| 120行スクロール相当 | 1,091.72ms | 1,096.56ms | +0.44% |

温まった巡回の組ごとの差の中央値は+0.47%、対応のある差の中央値を
bootstrapした95%区間は約-0.15〜+2.61%だった。旧測定の約8%増は、この条件で
持続する性能悪化としては再現しなかった。短時間のGPU readbackを含む測定・
少数反復・診断処理を含んだ旧結果から、単一原因を断定しない。

CPU側の追加処理は残る。別の**20組の診断**で、通常文字だけを対象に
Parleyの`set_fallback_chars()`の呼出しだけを外すと、3周目は約79.97msから
77.84msに減った（同じグリフ結果）。各クラスタの文字収集・SmallVec更新は
5,000件あたり約2〜3msの追加コストを説明する。診断用に呼出しを外した実装は
製品へ採用していない。OSへの問い合わせが通常文字で毎回増えたための遅延ではない。

## 実用操作と多言語

最終構成で、実在する多言語の**5,000ファイル**を本体のController / RowsModel /
一覧読み込みで開いた。GPU画像取得を含む測定であり、VSync込みのFPSではない。

| 実アプリの操作（各120回） | コールバックp95 | コールバック＋描画p95 | 最大（描画込み） |
| --- | ---: | ---: | ---: |
| ホイールと同じページ送り経路・前進 | 0.45ms | 9.95ms | 12.91ms |
| 同・後退 | 0.33ms | 9.14ms | 12.07ms |
| ↓キー移動 | 0.19ms | 7.75ms | 12.45ms |

初回の一覧準備は約412msだった（計測フック開始からであり、プロセス起動全体では
ない）。この環境では継続的な大きな遅延や表示の欠落は見られなかった。

表示部分のベンチでは、多言語5,000件の欠落グリフが3,750個から0個になった。
多言語条件は5組の反復で、温まった巡回は1,855.52ms → 1,897.92ms、
120行スクロール相当は1,051.14ms → 1,067.13ms。画面後のPrivate Bytesは
110.08MiB → 111.15MiB、Working Setは90.42MiB → 90.89MiBだった。
これらのメモリ差を文字キャッシュだけの割当量とは断定しない。

キャッシュ上限8,192の必要性は、2,048種類の拡張漢字を循環する別試験で確認した。
上限1,024では温まってもOSへ4,096回再問い合わせしたが、8,192では0回になり、
2周目は約88ms → 約43msとなった。キャッシュは無制限ではなく、さらに大きな
ワーキングセットでは再び追い出しが起こる。

## 測定条件と再確認

Windows 10 Pro 19045 / ja-JP、Ryzen 5 5600X、RTX 3060 Ti。
UIは1200×720、DPI倍率1、13px、名前列のみ。未修正・修正の実行順を交互にし、
速度測定とビルドを並行させていない。OSのフォントキャッシュはフラッシュしていない。
スナップショットの相対比較と実アプリの入力経路を分けて評価した。
Windows 11・全Unicode・すべてのフォント構成を検証済みとはしない。
OSが利用可能な字形を提供できない場合は、四角になることがある。

回帰テスト:

```powershell
cargo test --release --locked --manifest-path app/Cargo.toml
```

任意の表示・レイアウト計測ツールはfeatureで隔離してある。通常のビルドや
アプリの実行に計測処理は入らない。

```powershell
cargo run --release --locked --manifest-path app/Cargo.toml --features font-benchmark --example font-benchmark -- cpu plain results/font-cpu.json
cargo run --release --locked --manifest-path app/Cargo.toml --features font-benchmark --example font-benchmark -- ui mixed results/font-ui.json
```

`plain`は日本語・英数字、`mixed`は多言語、`diverse`は拡張漢字の厳しい条件。
ツールは自身のプロセスだけでフォント環境変数を外し、DPI倍率を1に固定する。
UI計測は本体と同じ`ui.slint`へページ単位でRowを供給する表示部分の測定で、
本体Controllerのディスク走査やOS入力から画面提示までの時間を含めない。
計数用Atomicを持たないため、このツールはOS問い合わせ回数を報告しない。

今回の生データと補足レポートはローカルの`results/font-pr689/`に保存。
将来の上流更新では、単体テストだけでなく多言語プレビューと同条件の反復測定を
再実行してから、2つの依存patchを外すこと。

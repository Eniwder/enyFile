# D&D実装と検証

## 実装方針

| 方法 | 実装負担・安全性・互換性 |
| --- | --- |
| HWNDのOLE `IDropTarget`から転送先のShell `IDropTarget`へ委譲（採用） | 既存のShellデータオブジェクトと`SHDoDragDrop`を維持できる。コピー・移動の選択、転送元への結果通知、衝突・権限・キャンセル・部分成功をWindows側で扱う。enyFile側に新しいコピー／移動エンジンを追加しない。 |
| Slint／winitのファイルドロップ通知で独自に実行 | Slint側の受付実装に加えて、OLEの操作効果の交渉・修飾キー・ドラッグ元への結果通知が必要。既存のパス転送ワーカーは再利用できるが、非同期転送の成功前にドラッグ元へ移動成功を返さないためのプロトコル管理も増える。 |

`main.rs`でwinitの既定の受付を解除してから、同じHWNDに独自の受付を登録する。Slintは実際のペイン配置に基づくヒット判定と強調表示を担当する。転送は転送先フォルダのShellターゲットへ委譲するため、貼り付けの独自衝突画面を経由せずWindows標準の確認画面になる。既存の貼り付け計画・置換処理は変更していない。

操作効果はドラッグ元が許すコピー・移動の範囲でShellが選ぶ。`DragEnter`／`DragOver`の結果がカーソルへ反映される。[MicrosoftのIDropTarget仕様](https://learn.microsoft.com/en-us/windows/win32/api/oleidl/nf-oleidl-idroptarget-dragenter)を参照。

内部ドラッグは既存の`SHDoDragDrop`実行中だけUIスレッドのスコープで識別する。設定が無効でも外部データは拒否しない。同一プロセスの同一ウィンドウ内を内部ドラッグとして扱い、別プロセスのenyFileからは外部ドロップとして扱う。

COMインターフェイスはすべてウィンドウのOLE STA内で保持・解放する。登録はRAIIで解除し、データオブジェクトは離脱・ドロップで解放する。Shellがメッセージを処理して再入する可能性があるため、Shell呼び出し中はControllerや状態のRefCellの借用を保持しない。

転送先が変わったときとドロップ直前に既存のファイルID・祖先判定を再利用する。同じ場所・自身の配下・不存在を含むバッチは全体を拒否する。フォルダ行のアイコン・名前列はそのフォルダ（「..」は親）、名前列以外・通常ファイル・余白は表示フォルダが転送先になる。名前列の境界はSlintの実際の列配置から取得し、フォルダ内への転送時だけ名前列を強調する。検索・比較結果、ドライブ行、モーダル画面・メニュー表示中、既存のファイル操作中は拒否する。

パス検証とShellターゲットへの接続はSTA上で行うため、遅い共有やShell拡張によりドラッグ中に待つ可能性がある。安全判定の後からShell実行までの間に外部プロセスがパスを差し替える競合は完全には排除できない。キャンセルは完了した転送の巻き戻しを保証せず、権限や個々の項目の失敗に関する最終的な判断・表示はShellに従う。
